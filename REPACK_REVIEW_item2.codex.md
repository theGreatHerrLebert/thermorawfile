**Findings**
1. **Medium: simulator deferral can blow memory on large overflow sets.**  
   `write_scan` clones every over-budget payload into `DeferredEdit.peaks`, then `finalize` builds all replacement packets, and `repack_many` also allocates a full `new_data` copy before splicing. For a 1 GB raw this is already roughly raw bytes + rebuilt data section + all cloned peaks + all replacement packets. See `repack_many` packet staging and full data rebuild at [src/lib.rs](/home/administrator/thermo-raw-spike/thermorawfile/src/lib.rs:1935) and [src/lib.rs](/home/administrator/thermo-raw-spike/thermorawfile/src/lib.rs:1974). For “most scans overflow” this is the main operational risk. Building deferred packets earlier and retaining packet bytes instead of peak clones would cap this better, though `repack_many` still duplicates the data section.
2. **Medium: finalize ordering depends on what `is_complete` / zero-residual actually checks.**  
   In the simulator diff, deferred scans are pushed during `write_scan`, while the packet is not rewritten until `finalize`. This is sound if completeness only means “cursor consumed enough template slots”, because the cursor advances once per descriptor and duplicates are impossible through normal `write_scan`. It is not sound if the zero-residual check inspects authored packet contents before the deferred `repack_many`: `author_centroids` and `author_profile` return over-budget before mutating or zeroing slack ([src/lib.rs](/home/administrator/thermo-raw-spike/thermorawfile/src/lib.rs:1095), [src/lib.rs](/home/administrator/thermo-raw-spike/thermorawfile/src/lib.rs:1564)), so deferred slots still contain template signal until after the check. Apply deferred edits before any byte-level residual validation.
3. **Low/Medium: malformed packet bounds can still panic or read across packets.**  
   The builders validate `pkt + old_len <= bytes.len()` ([src/lib.rs](/home/administrator/thermo-raw-spike/thermorawfile/src/lib.rs:1690), [src/lib.rs](/home/administrator/thermo-raw-spike/thermorawfile/src/lib.rs:2046)), but then read fixed header/count fields like `pkt..pkt+44` using unchecked slices. On a corrupt short `DataPacketSize`, this can read into the next packet or panic rather than returning `io::Error`. Normal fixtures and RawFileReader validation will not catch this unless such malformed packets are tested.
**Core `repack_many` Assessment**
I do not see a correctness bug in the main single-splice algorithm under its stated precondition. The contiguity check requires `index[j].offset == cumulative_size` in scan order ([src/lib.rs](/home/administrator/thermo-raw-spike/thermorawfile/src/lib.rs:1955)), then the rebuild assigns fresh offsets from the new layout ([src/lib.rs](/home/administrator/thermo-raw-spike/thermorawfile/src/lib.rs:1977)). Relocating at `old_data_end` by total `delta` is the right boundary for everything after the data section ([src/lib.rs](/home/administrator/thermo-raw-spike/thermorawfile/src/lib.rs:1991)). Index offsets and sizes are then rewritten once ([src/lib.rs](/home/administrator/thermo-raw-spike/thermorawfile/src/lib.rs:1995)).
Edge cases look handled: empty edits return no-op; duplicate and out-of-range scans error before mutation; centroid/profile mixing is fine as long as each edit matches the existing packet type; shrinking works because `delta` can be negative and offsets are recomputed from the new data layout. The `HashMap` iteration order only affects stats write order, not bytes in the data section.
**Single-Scan Refactor**
The single-scan path still computes `pkt`, `old_len`, splices, relocates, rewrites offsets, and writes stats ([src/lib.rs](/home/administrator/thermo-raw-spike/thermorawfile/src/lib.rs:1664), [src/lib.rs](/home/administrator/thermo-raw-spike/thermorawfile/src/lib.rs:1791)). I do not see an intended behavior change from the refactor itself. One subtle change is that `write_index_offsets` now rewrites `DataPacketSize` for every scan-index entry, not only the edited one ([src/lib.rs](/home/administrator/thermo-raw-spike/thermorawfile/src/lib.rs:1887)); for a normal parsed model this is byte-preserving, but it is broader write surface than before.
**Validation Gaps**
The byte-equivalence test covers centroid growth, scan-order edits, one fixture, and the current single-scan implementation as oracle. It would not catch profile repack regressions, shrink cases, unordered edit lists, populated `Offset32` files, non-contiguous data-section fallbacks, malformed short packets, hidden/internal pointers inside method/log/tune streams, or simulator isolation metadata after deferred growth. RawFileReader scan validation also may not exercise all controller metadata or internal section pointers.
